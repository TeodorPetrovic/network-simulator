Vežba 6, Zadatak 1 – Rešenje (komande)

Sve komande su kucane na pravim Docker uređajima (gns3/openvswitch i alpine) i proverene u ovom redosledu. OVS1 radi kao ruter bez ijednog NORMAL pravila: na ARP zahteve za gateway adrese odgovara ARP-responder pravilima, a IP pakete rutira pravilima koja menjaju MAC adrese, smanjuju TTL i biraju izlazni port.

Korak 2 – MAC adrese, IP adrese i podrazumevani izlaz

PC1

ip link set eth0 down
ip link set eth0 address 02:00:00:00:01:11
ip link set eth0 up
ip addr add 10.16.1.11/24 dev eth0
ip route add default via 10.16.1.1

PC2

ip link set eth0 down
ip link set eth0 address 02:00:00:00:01:12
ip link set eth0 up
ip addr add 10.16.1.12/24 dev eth0
ip route add default via 10.16.1.1

SERVER

ip link set eth0 down
ip link set eth0 address 02:00:00:00:02:64
ip link set eth0 up
ip addr add 10.16.2.100/24 dev eth0
ip route add default via 10.16.2.1

Podrazumevani izlaz znači: za sve adrese van svoje podmreže uređaj šalje okvir MAC adresi gateway-a. Zato će PC1 pre slanja paketa ka SERVER-u tražiti ARP-om MAC adresu za 10.16.1.1.

Korak 3 – početno stanje

OVS1

ovs-vsctl show

Slika pri pokretanju sama stavlja sve portove u br0 (u izlazu se vide i prazni br1–br3):

    Bridge br0
        datapath_type: netdev
        Port eth0
            Interface eth0
        Port eth1
            Interface eth1
        Port eth2
            Interface eth2
        Port br0
            Interface br0
                type: internal
    Bridge br1
        ...

PC1

ping -c 2 -W 2 10.16.1.12
ping -c 2 -W 2 10.16.2.100

Ping ka PC2 uspeva (0% packet loss, ttl=64): PC1 i PC2 su u istoj podmreži i br0 radi kao običan svič (pravilo NORMAL). Ping ka SERVER-u ne uspeva (100% packet loss): SERVER je u drugoj podmreži, pa PC1 šalje ARP zahtev za gateway 10.16.1.1, a tu adresu nema nijedan uređaj. Svič ne rutira; za to je potreban ruter.

Korak 5 – brisanje NORMAL pravila

OVS1

ovs-ofctl dump-flows main-net
ovs-ofctl del-flows main-net
ovs-ofctl dump-flows main-net

Prvi dump-flows pokazuje jedino pravilo priority=0 actions=NORMAL, a drugi, posle del-flows, ne pokazuje nijedno pravilo (samo liniju NXST_FLOW reply):

NXST_FLOW reply (xid=0x4):
 cookie=0x0, duration=0.015s, table=0, n_packets=0, n_bytes=0, idle_age=0, priority=0 actions=NORMAL
NXST_FLOW reply (xid=0x4):

PC1

ping -c 2 -W 2 10.16.1.12

Ping ne uspeva. Bridge bez pravila nema šta da uradi sa okvirom, pa ga odbacuje: nema ni prosleđivanja, ni učenja MAC adresa, ni ARP-a.

Korak 6 – pravila za komunikaciju unutar iste podmreže

OVS1

ovs-ofctl add-flow main-net 'priority=140,arp,arp_op=1,in_port=eth0,actions=output:eth1'
ovs-ofctl add-flow main-net 'priority=140,arp,arp_op=1,in_port=eth1,actions=output:eth0'
ovs-ofctl add-flow main-net 'priority=150,dl_dst=02:00:00:00:01:11,actions=output:eth0'
ovs-ofctl add-flow main-net 'priority=150,dl_dst=02:00:00:00:01:12,actions=output:eth1'

Prva dva pravila prosleđuju ARP zahtev sa jednog računara na drugi, a druga dva, prema odredišnoj MAC adresi, isporučuju svaki okvir (ARP odgovor i IP paket) pravom računaru. To je ponašanje običnog sviča sa fiksnom tabelom MAC adresa. Pravila sa dl_dst imaju viši prioritet od budućih pravila za rutiranje, jer okviri adresirani direktno na računar ne smeju da se rutiraju.

PC1

ip neigh flush dev eth0
ping -c 2 -W 2 10.16.1.12

PC2

ip neigh flush dev eth0

Ping uspeva i u odgovoru je ttl=64: početna vrednost TTL-a (64) nije smanjena, jer paket nije prošao kroz ruter, nego samo kroz svič.

Korak 7 – ARP-responder pravila za gateway adrese

OVS1

ovs-ofctl add-flow main-net 'priority=200,arp,arp_op=1,arp_tpa=10.16.1.1,actions=move:NXM_OF_ETH_SRC[]->NXM_OF_ETH_DST[],mod_dl_src:02:00:00:00:01:01,load:0x2->NXM_OF_ARP_OP[],move:NXM_NX_ARP_SHA[]->NXM_NX_ARP_THA[],move:NXM_OF_ARP_SPA[]->NXM_OF_ARP_TPA[],load:0x020000000101->NXM_NX_ARP_SHA[],load:0x0a100101->NXM_OF_ARP_SPA[],in_port'
ovs-ofctl add-flow main-net 'priority=200,arp,arp_op=1,arp_tpa=10.16.2.1,actions=move:NXM_OF_ETH_SRC[]->NXM_OF_ETH_DST[],mod_dl_src:02:00:00:00:02:01,load:0x2->NXM_OF_ARP_OP[],move:NXM_NX_ARP_SHA[]->NXM_NX_ARP_THA[],move:NXM_OF_ARP_SPA[]->NXM_OF_ARP_TPA[],load:0x020000000201->NXM_NX_ARP_SHA[],load:0x0a100201->NXM_OF_ARP_SPA[],in_port'

Pravilo hvata ARP zahtev (arp_op=1) čija je tražena adresa (arp_tpa) gateway, i od istog paketa pravi odgovor: (1) odredišna MAC adresa okvira postaje izvorišna, a izvorišna MAC adresa postaje MAC "rutera" (02:00:00:00:01:01); (2) operacija ARP paketa postaje 2 (odgovor); (3) u ARP paketu se stari pošiljalac (ARP_SHA, ARP_SPA) kopira u cilj (ARP_THA, ARP_TPA); (4) pošiljalac postaje "ruter": MAC adresa 02:00:00:00:01:01 i IP adresa 10.16.1.1 upisuju se kao brojevi (0x020000000101 je MAC bez dvotačaka, 0x0a100101 je IP adresa 10.16.1.1 u heksadecimalnom zapisu: 10 = 0x0a, 16 = 0x10, 1 = 0x01, 1 = 0x01); (5) in_port šalje odgovor nazad na port sa kog je zahtev stigao. Pravilo ima viši prioritet (200) od pravila za običan ARP (140), pa zahtev za gateway nikada ne stiže do drugog računara.

PC1

ping -c 1 -W 1 10.16.1.1
ip neigh show 10.16.1.1

SERVER

ping -c 1 -W 1 10.16.2.1
ip neigh show 10.16.2.1

Ping na gateway ne uspeva (nema pravila koje odgovara na ICMP), ali ip neigh show sada prikazuje adresu lladdr 02:00:00:00:01:01 za 10.16.1.1 na PC1, odnosno lladdr 02:00:00:00:02:01 za 10.16.2.1 na SERVER-u, u stanju REACHABLE (ili STALE). Znači, ARP-responder radi: računari su dobili MAC adresu uređaja koji ne postoji.

Korak 8 – pravila za rutiranje

OVS1

ovs-ofctl add-flow main-net 'priority=100,ip,nw_dst=10.16.2.0/24,actions=mod_dl_src:02:00:00:00:02:01,mod_dl_dst:02:00:00:00:02:64,dec_ttl,output:eth2'
ovs-ofctl add-flow main-net 'priority=100,ip,nw_dst=10.16.1.11,actions=mod_dl_src:02:00:00:00:01:01,mod_dl_dst:02:00:00:00:01:11,dec_ttl,output:eth0'
ovs-ofctl add-flow main-net 'priority=100,ip,nw_dst=10.16.1.12,actions=mod_dl_src:02:00:00:00:01:01,mod_dl_dst:02:00:00:00:01:12,dec_ttl,output:eth1'

Svako pravilo radi ono što radi ruter: mod_dl_src postavlja izvorišnu MAC adresu na MAC adresu interfejsa rutera kroz koji paket izlazi (02:00:00:00:02:01 u podmreži SERVER-a, 02:00:00:00:01:01 u podmreži računara), mod_dl_dst postavlja MAC adresu odredišnog uređaja (statički, jer OVS1 ne šalje ARP), dec_ttl smanjuje TTL za jedan i output šalje paket na izlazni port. IP adresa se ne menja.

PC1

ping -c 2 -W 2 10.16.2.100
ping -c 2 -W 2 -t 1 10.16.2.100

PC2

ping -c 2 -W 2 10.16.2.100

SERVER

ping -c 2 -W 2 10.16.1.11

Svi pingovi bez -t 1 uspevaju, a u odgovoru je ttl=63, jedan manje nego pri pingu PC1 – PC2 (ttl=64): odgovor SERVER-a kreće sa TTL 64, prolazi kroz pravilo sa dec_ttl i do računara stiže sa 63. Ping sa -t 1 šalje zahtev sa TTL 1: dec_ttl ga ne može smanjiti, pa se paket odbacuje i odgovor ne stiže (100% packet loss). Tako se ponaša i pravi ruter: paket kome je TTL istekao ne prosleđuje dalje.

Korak 9 – brojači pravila

OVS1

ovs-ofctl --names dump-flows main-net

Izlaz (skraćeno; vrednosti brojača zavise od toga šta je sve poslato):

... n_packets=2, n_bytes=84, priority=200,arp,arp_tpa=10.16.1.1,arp_op=1 actions=move:NXM_OF_ETH_SRC[]->NXM_OF_ETH_DST[],mod_dl_src:02:00:00:00:01:01,...,IN_PORT
... n_packets=1, n_bytes=42, priority=200,arp,arp_tpa=10.16.2.1,arp_op=1 actions=move:NXM_OF_ETH_SRC[]->NXM_OF_ETH_DST[],mod_dl_src:02:00:00:00:02:01,...,IN_PORT
... n_packets=3, n_bytes=238, priority=150,dl_dst=02:00:00:00:01:11 actions=output:eth0
... n_packets=3, n_bytes=238, priority=150,dl_dst=02:00:00:00:01:12 actions=output:eth1
... n_packets=1, n_bytes=42, priority=140,arp,in_port=eth0,arp_op=1 actions=output:eth1
... n_packets=1, n_bytes=42, priority=140,arp,in_port=eth1,arp_op=1 actions=output:eth0
... n_packets=7, n_bytes=686, priority=100,ip,nw_dst=10.16.2.0/24 actions=mod_dl_src:02:00:00:00:02:01,mod_dl_dst:02:00:00:00:02:64,dec_ttl,output:eth2
... n_packets=3, n_bytes=294, priority=100,ip,nw_dst=10.16.1.11 actions=mod_dl_src:02:00:00:00:01:01,mod_dl_dst:02:00:00:00:01:11,dec_ttl,output:eth0
... n_packets=2, n_bytes=196, priority=100,ip,nw_dst=10.16.1.12 actions=mod_dl_src:02:00:00:00:01:01,mod_dl_dst:02:00:00:00:01:12,dec_ttl,output:eth1

Pravila koja su se koristila imaju n_packets veće od nule (tačne vrednosti variraju). ARP-responder pravila su porasla pri razrešavanju MAC adresa gateway-a, a pravilo nw_dst=10.16.2.0/24 pri pingovima ka SERVER-u. Odgovor SERVER-a ka PC1 ne treba posebno pravilo: to je običan IP paket sa odredištem 10.16.1.11, pa ga hvata pravilo nw_dst=10.16.1.11 i vraća ga kroz isti "ruter". Ping PC1 – PC2 ne povećava ni jedno pravilo nw_dst, nego pravila dl_dst i ARP pravila: PC1 šalje okvir direktno na MAC adresu PC2 (ne na MAC adresu gateway-a), pa ga pravilo višeg prioriteta isporučuje bez rutiranja i bez smanjenja TTL-a, a pravilo za rutiranje do njega ni ne dolazi. (Brojač pravila nw_dst=10.16.1.12 raste samo zbog odgovora SERVER-a na pingove sa PC2.)

Korak 10 – ACL pravilo

OVS1

ovs-ofctl add-flow main-net 'priority=300,ip,nw_src=10.16.1.12,nw_dst=10.16.2.0/24,actions=drop'

PC1

ping -c 2 -W 2 10.16.2.100

PC2

ping -c 2 -W 2 10.16.2.100
ping -c 2 -W 2 10.16.1.11

OVS1

ovs-ofctl --names dump-flows main-net | grep drop
... n_packets=2, n_bytes=196, priority=300,ip,nw_src=10.16.1.12,nw_dst=10.16.2.0/24 actions=drop

Ping PC1 – SERVER uspeva, ping PC2 – SERVER ne uspeva (100% packet loss), a ping PC2 – PC1 uspeva (ttl=64, jer se ne rutira). Paket sa PC2 ka podmreži 10.16.2.0/24 odgovara i ACL pravilu i pravilu za rutiranje, a OVS izvršava pravilo višeg prioriteta: priority=300 je veći od 100, pa paket biva odbačen i pravilo za rutiranje ga ne vidi. Brojač ACL pravila je porastao (ovde 2, po jedan za svaki ping zahtev). Da je ACL pravilo imalo prioritet niži od 100, paket bi bio rutiran, a ACL pravilo nikada ne bi bilo izabrano. Saobraćaj PC2 – PC1 ne odgovara ACL pravilu (odredište nije u podmreži 10.16.2.0/24).
