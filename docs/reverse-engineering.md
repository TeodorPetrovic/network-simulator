## Observed behavior

### API version alignment

The GNS3 server 3.1 snapshot registers its controller routes under `/v3` in [`api/server.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/api/server.py#L108-L116), and its OpenAPI document lists controller routes under `/v3`. The supplied Web UI `master` snapshot prepends `/v2` to HTTP requests in [`http-server.service.ts`](https://github.com/GNS3/gns3-web-ui/blob/87fe78074efa631c72fbf8f29907198f3b803aa4/src/app/services/http-server.service.ts#L174-L194) and uses `/v2` WebSocket URLs in [`notification.service.ts`](https://github.com/GNS3/gns3-web-ui/blob/87fe78074efa631c72fbf8f29907198f3b803aa4/src/app/services/notification.service.ts#L7-L23).

These two branch snapshots do not line up for direct client/server use. The first API increment targets the server 3.1 `/v3` contract. A `/v2` compatibility shim for this Web UI snapshot is a separate follow-up, after the `/v3` behavior is in place.

### Project and topology data

- The Web UI requests project nodes, then links, then drawings when loading a project. It installs the project WebSocket after those requests finish. See [`project-map.component.ts`](https://github.com/GNS3/gns3-web-ui/blob/87fe78074efa631c72fbf8f29907198f3b803aa4/src/app/components/project-map/project-map.component.ts#L440-L477) and [`project.service.ts`](https://github.com/GNS3/gns3-web-ui/blob/87fe78074efa631c72fbf8f29907198f3b803aa4/src/app/services/project.service.ts#L26-L56).
- Project notification frames carry an `action` and an `event`; the UI applies `node.*`, `link.*`, and `drawing.*` actions to in-memory data sources. See [`project-web-service-handler.ts`](https://github.com/GNS3/gns3-web-ui/blob/87fe78074efa631c72fbf8f29907198f3b803aa4/src/app/handlers/project-web-service-handler.ts#L9-L75).
- The server serializes project metadata and topology collections (`nodes`, `links`, `computes`, `drawings`) into its `.gns3` JSON format with a format revision. See [`topology.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/controller/topology.py#L73-L128).
- Node deletion removes attached links before destroying the node, then saves the topology and emits a deletion notification. Node creation is idempotent for an existing node ID and persists/emits after creation. See [`project.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/controller/project.py#L666-L750).
- The server writes a temporary topology file and moves it into place after JSON serialization. Starting all nodes uses a bounded concurrency pool. See [`project.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/controller/project.py#L2270-L2297).
- The server exposes a project notification WebSocket; clients receive one JSON notification per frame. See [`projects.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/api/routes/controller/projects.py#L640-L670).

### Runtime templates and node lifecycle

- The server lists templates through `GET /v3/templates` and creates a project node from a template through `POST /v3/projects/{project_id}/templates/{template_id}` with a `TemplateUsage` body (`x`, `y`, optional name and compute ID). See [`templates.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/api/routes/controller/templates.py#L187-L235) and [`projects.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/api/routes/controller/projects.py#L1017-L1040).
- Node power operations are separate `start`, `stop`, `suspend`, and `reload` routes. The controller waits for a target state only when the caller asks it to; unsupported suspend is an error. See [`nodes.py`](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/api/routes/controller/nodes.py#L449-L525).
- Docker nodes use an image and adapter count, then the compute side owns actual container lifecycle and networking. QEMU templates instead refer to a disk image, memory, CPU count, and adapter configuration; QEMU process startup and QMP control live in the compute implementation. See the pinned [`qemu_vm.py` lifecycle](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/compute/qemu/qemu_vm.py#L1094-L1170) and [network argument construction](https://github.com/GNS3/gns3-server/blob/149549e02986aa76d806b92b04cb36ad91786223/gns3server/compute/qemu/qemu_vm.py#L2590-L2640). This migration implements real Docker containers and QEMU processes; homogeneous QEMU segments still use its multicast socket backend, while mixed-runtime links attach to a shared uBridge kernel bridge.
- VPCS is not a QEMU disk appliance: GNS3 launches the standalone VPCS process with one PC instance, a TCP console port, and local/remote UDP ports for its Ethernet frames. Its compute adapter binds the node's NIO to uBridge. The Rust adapter follows that process shape, retains its local UDP switch for VPCS-only links, and uses uBridge's UDP-to-TAP endpoint for mixed-runtime links. It negotiates the VPCS Telnet console before proxying it to the browser. See the GNS3 3.1 [`vpcs_vm.py` command construction and UDP NIO setup](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/vpcs/vpcs_vm.py#L700-L781), [VPCS UDP frame I/O](https://github.com/GNS3/vpcs/blob/master/src/dev.c#L53-L158), and [VPCS license](https://github.com/GNS3/vpcs/blob/master/COPYING).
- Cisco's classic IOS router images are a separate Dynamips runtime; IOSv and IOSvL2 virtual appliances are QEMU machines. The GNS3 3.1 adapter starts a Dynamips hypervisor, configures a VM through its TCP text protocol, selects a platform and IOS image, then attaches adapter ports through NIO bindings. This implementation independently follows that behavior for c7200 and `C7200-IO-FE`; it checks the IOS ELF header, exposes an image upload route, configures RAM/idle-PC/startup config/console, and connects the router UDP NIO to the VPCS segment switch. The server requires Dynamips 0.2.11 or newer. The real hypervisor protocol and router object creation are integration-tested, but IOS boot remains unverified until a licensed image is supplied. See GNS3's [`dynamips` manager](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/dynamips/__init__.py), [hypervisor command transport](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/dynamips/dynamips_hypervisor.py), [router VM setup](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/dynamips/nodes/router.py), [c7200 slot defaults](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/dynamips/nodes/c7200.py), [GNS3's emulator comparison](https://docs.gns3.com/docs/emulators/which-emulators-should-i-use), and [Dynamips template setup](https://docs.gns3.com/docs-3.1-en/web-ui/template-preferences-dynamips).
- GNS3 3.1 creates Docker containers with `Tty` and `OpenStdin` enabled and `StdinOnce` disabled, and exposes a Docker node console WebSocket at `/projects/{project_id}/docker/nodes/{node_id}/console/ws`. It streams the Docker attach socket in both directions. The same implementation starts auxiliary consoles with `script -qfc` around `docker exec -i -t`, confirming that the `script` utility is a runtime dependency for local PTY-backed Docker sessions. See the [3.1 Docker compute implementation](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/docker/docker_vm.py) and [Docker console route](https://github.com/GNS3/gns3-server/blob/master/gns3server/handlers/api/compute/docker_handler.py#L1827-L1846). This migration enables Docker TTYs at container creation and bridges `docker attach` over its matching `/v3/compute/.../docker/.../console/ws` route; it sends Docker's detach key sequence on WebSocket close so a running interactive node can be reattached.
- The current GNS3 compute API exposes `/projects/{project_id}/qemu/nodes/{node_id}/console/ws`; the Web UI attaches an xterm terminal to a WebSocket, and the compute base node forwards text/binary input and console output in both directions. See the [QEMU WebSocket route](https://github.com/GNS3/gns3-server/blob/master/gns3server/handlers/api/compute/qemu_handler.py#L2407-L2426), [3.1 console relay](https://github.com/GNS3/gns3-server/blob/3.1/gns3server/compute/base_node.py#L3017-L3107), and [Web UI terminal](https://github.com/GNS3/gns3-web-ui/blob/87fe78074efa631c72fbf8f29907198f3b803aa4/src/app/components/web-console-full-window/web-console-full-window.component.ts#L526-L578). This controller uses the corresponding `/v3/compute/...` route and bridges a raw QEMU serial socket. A temporary bootable serial-echo guest verified both directions; vendor guest images and Telnet negotiation remain to be checked for wider compatibility.

### Image search and GNS3 appliance definitions

**Observation:** the GNS3 Marketplace distributes appliance definitions as `.gns3a` files. They describe a device template and may name VM/IOS files that the user supplies separately; the `.gns3` extension is used for project/lab files. GNS3's [Marketplace install instructions](https://docs.gns3.com/docs/using-gns3/beginners/install-from-marketplace) and [file format reference](https://api.gns3.net/en/2.0/file_format.html) establish this distinction and explicitly describe the separate Cisco image requirement. The catalog integration therefore searches the upstream [GNS3 appliance registry](https://github.com/GNS3/gns3-registry/tree/master/appliances), fetches actual `.gns3a` JSON on selection, validates its appliance UUID and name, and imports that definition under `data/appliances` (overridable with `NETWORK_SIMULATOR_APPLIANCES`). If its declared image already exists in the matching local runtime directory, `/v3/templates` exposes an enriched template based on registry settings. Importing metadata does not fabricate or fetch the runtime image.

**Observation:** [iShare2 CLI](https://github.com/ishare2-org/ishare2-cli) searches image records in the separate LabHub index and its installer targets EVE-NG/UNetLab directories; the CLI checks for root privileges. This app queries the published `labhub.json` release asset for names, types, sizes and file counts, but does not copy the GPL-3.0 CLI code or run its installer. Users still need to ensure they have rights to image files and place them in the appropriate local image directory. Catalog results are cached in memory for 30 minutes; the index download has a 32 MiB limit and individual appliance definitions are limited to 2 MiB. The search and import handlers are `GET /v3/marketplace/ishare2/images`, `GET /v3/marketplace/gns3/appliances`, `GET /v3/marketplace/gns3/appliances/{file_name}`, and `POST /v3/marketplace/gns3/appliances/{file_name}/import`.

**Implementation:** runtime base images are global, not stored under project directories. The default root is `$XDG_DATA_HOME/network-simulator/images`, falling back to `~/.local/share/network-simulator/images`; `NETWORK_SIMULATOR_IMAGE_HOME` changes the root and per-runtime `NETWORK_SIMULATOR_QEMU_IMAGES` / `NETWORK_SIMULATOR_DYNAMIPS_IMAGES` variables can split it. Startup creates the selected runtime folders. The project topology stores a reference to the shared base image; QEMU writes each node's copy-on-write overlay under its separate runtime state directory. Docker uses its own global Engine image store, while VPCS uses a host executable and needs no VM image. QEMU uploads are streamed, limited to 64 GiB, checked with `qemu-img info`, and installed atomically in the global library; Dynamips uploads retain the ELF validation.

### Engineering implications

**Observation:** the UI installs its event stream after separately fetching nodes, links, and drawings. **Inference:** a concurrent edit between the snapshot reads and WebSocket subscription could leave a client with stale state unless another refresh occurs. The source does not prove this race occurs in normal use. The Rust design should make initial snapshots and event cursors consistent, then support replay from a durable sequence number.

**Observation:** each ordinary topology mutation can serialize and replace the full `.gns3` file. **Inference:** frequent edits in large projects may do avoidable disk work. A transactional store can commit the topology change and event record together, then checkpoint snapshots asynchronously. The existing temporary-file replacement is a useful crash-safety behavior to preserve for exports/backups.

**Observation:** the server delegates device work to several external runtimes (QEMU/KVM, Docker, VPCS, Dynamips, and others). A faithful replacement therefore has a much larger scope than reimplementing the graph model. The Rust controller has separate runtime services and routes mixed-runtime Ethernet links through uBridge's host L2 datapath. A live controller API test passed ICMP between Alpine Docker and VPCS after granting uBridge `CAP_NET_ADMIN`/`CAP_NET_RAW`; mixed QEMU and booted Dynamips router paths still need packet tests.

## Architecture and next boundaries

The original architecture proposal is partially implemented. Current code keeps runtime process details out of the topology store and persists the metadata needed to reattach to each VM/container after restart. The next boundaries to extract are:

1. **Domain core:** projects, nodes, interfaces, links, runtime state transitions, validation, and typed errors. No HTTP or database types in the core.
2. **Persistence:** SQLite with WAL and migrations for project/topology state, a monotonically increasing per-project revision, and an outbox/event sequence committed in the same transaction as each mutation.
3. **API and event transport:** async HTTP plus WebSocket or SSE. Mutations support idempotency keys; clients can resume from an event cursor. A snapshot includes the cursor it represents.
4. **Runtime adapters:** async lifecycle interfaces for supported emulator/container types, with explicit timeouts, cancellation, health checks, and cleanup on partial failure.
5. **UI:** use TanStack Start with React and TypeScript for a same-origin static SPA; retain a Rust/WASM module only for measured CPU-heavy browser work.

The main performance strategy is bounded parallelism for independent node lifecycle work, indexed topology lookups, batched persistence, and avoiding full topology serialization on every UI interaction. The main reliability strategy is transactionally coupled state/events, replayable events, validated graph mutations, bounded external process calls, and recovery from partially completed adapter operations.

## Implemented first slice

The initial Rust service binds to loopback by default and exposes a selected `/v3` controller surface:

- Project list/create/read/update/delete and open/close.
- Node, link, and drawing list/create/read/update/delete.
- Link endpoint validation and automatic removal of attached links when deleting a node.
- `GET /v3/projects/{id}/topology` reads the project, topology collections, and event cursor in one SQLite read transaction.
- Project WebSocket notifications persist to an event table in the same write transaction as the topology change. Clients can resume with `?after=<event_cursor>`; broadcast lag falls back to replay from SQLite.

SQLite uses WAL with full synchronous commits. Topology objects retain their GNS3-shaped JSON fields, including fields the controller does not interpret yet. This makes the early API extensible while keeping common lookups indexed. The topology subset now has three executable local runtimes:

- **Docker:** installed-image templates, stopped interactive-TTY container creation, optional per-node command arguments, lifecycle operations, isolated internal bridge networks for Docker-only Ethernet links, runtime state refresh, cleanup, and a WebSocket console attached to the running node's main TTY. Mixed-runtime endpoints use a veth moved into the stopped container's network namespace when it starts.
- **QEMU:** disk-image templates under a configurable directory, `qemu-img` copy-on-write overlays per node, daemonized processes with pidfiles and logs, QMP status/start/stop/suspend/resume/reset operations, KVM when `/dev/kvm` is accessible with TCG fallback, QEMU multicast for QEMU-only segments, and TAP attachments for mixed-runtime links. A segment uses each endpoint's configured adapter and must be created or deleted while attached VMs are stopped. Runtime status reports whether the service account can access KVM and why when it cannot.
- **VPCS:** executable detection and a built-in template, process lifecycle and cleanup, startup scripts, Telnet-negotiated browser console, one UDP Ethernet adapter per PC, and a Rust layer-2 forwarding path for multi-node VPCS segments. An integration test builds the upstream executable and verifies ICMP ping between two VPCS nodes. The upstream binary is an external dependency; its source is not copied into this project.
- **Dynamips:** external executable detection (minimum version 0.2.11), IOS image listing/upload with header validation, c7200 router creation, RAM and idle-PC settings, startup config, start/stop/suspend/reload, live status, WebSocket console, and a UDP NIO joined to the VPCS/Dynamips Ethernet segment. A real upstream Dynamips binary is used by the ignored protocol integration test to create/remove a c7200 instance and bind/remove its real UDP NIO. The test does not boot a router because this repository has no Cisco image.

QEMU process, QMP, and serial socket paths are persisted with each node so the controller can reconnect after a service restart. Older nodes without a serial path derive it from the persisted QMP socket location. Disk selection is constrained to canonical files under the configured image directory. Authentication, `/v2`, `.gns3` import/export, remote compute registration, additional hypervisors, virtual Ethernet switches, Docker terminal resizing, and fuller template settings remain future work.

## Frontend migration

The frontend uses TanStack Start with React and TypeScript in SPA mode. Its build emits `frontend/dist/client/index.html` and static assets; the Rust service serves the app shell for browser routes and serves the app and `/v3` API from the same origin. Node is a build-time dependency only. The Vite development server proxies API and WebSocket traffic to the Rust controller.

The first UI flow follows the observed Web UI sequence: list projects, create or open a project, load nodes/links/drawings from one topology snapshot, then connect to its event stream using that snapshot's cursor. The upstream project map currently reads the three topology collections in sequence and installs its WebSocket after those reads. The Rust UI uses the atomic snapshot and replay cursor already implemented on the controller. Its event reducer handles `node.*`, `link.*`, and `drawing.*` create/update/delete messages in the shape used by the observed project event handler.

The browser supports project creation/list/open/close/delete; adding Docker containers from installed images, QEMU VMs from local disk images, VPCS nodes, and c7200 IOS routers; per-container command overrides, VPCS startup scripts, Dynamips IOS upload, RAM, idle-PC and startup configuration; lifecycle controls where supported; xterm terminals for running QEMU, Docker, VPCS, and Dynamips nodes; creating and deleting supported Ethernet segments; dragging nodes; and applying live server events. VPCS and Dynamips can share a UDP Ethernet segment; mixed-runtime links use one Linux bridge with runtime-specific physical endpoints. The bridge create path and Alpine Docker↔VPCS ICMP have passed live validation with upstream uBridge capabilities. Mixed QEMU/VPCS and booted Dynamips/IOS packet paths remain unverified. Stored drawings render after parsing and rebuilding their SVG through an allowlist of elements and attributes; scripts, event handlers, external references, and unsupported elements are removed. The UI does not yet create or edit drawings. Template, lifecycle, and console flows use GNS3-shaped `/v3` routes.

The UI intentionally uses the local server's `/v3` routes rather than copying the supplied UI snapshot's `/v2` base URL. Keep browser interactions in TypeScript while they are event and network bound. Consider a Rust/WASM module only after measurements show a CPU-bound browser task such as layout on large graphs; the current canvas does not warrant a WASM dependency.

Frontend tests cover API route/body formation, Dynamips image upload and console URLs, project create/open, snapshot loading, Docker/QEMU/Dynamips template-backed node creation, console panels, live node events, SVG sanitization, and event reducer idempotence. Rust API tests cover Docker/QEMU node creation and lifecycle, Docker TTY WebSocket input/output, QEMU private disk overlays and QMP lifecycle, generated link endpoints, duplicate port rejection, consistent snapshots, and cleanup. The optional live checks are ignored by default. Run `NETWORK_SIMULATOR_TEST_VPCS=/path/to/vpcs cargo test vpcs_ -- --ignored` for upstream VPCS process, console, and ping coverage; `NETWORK_SIMULATOR_TEST_DYNAMIPS=/path/to/dynamips cargo test dynamips::tests::upstream_dynamips_creates_and_reports_a_real_c7200_hypervisor_instance -- --ignored` for the real Dynamips protocol; and `cargo test runtime::tests::alpine_containers_exchange_packets_over_a_real_link_network -- --ignored` for real Docker bridge/ICMP coverage. The Dynamips protocol check proves hypervisor configuration, not IOS boot.

## Next roadmap

1. Verify c7200 IOS boot, startup config, console, and ping with a licensed image supplied by the operator.
2. Grant uBridge its required capabilities and run mixed Docker/VPCS, QEMU/VPCS, and licensed Dynamips packet tests; verify restart/cleanup behavior on the kernel bridge.
3. Check QEMU console compatibility against vendor guest images and Telnet behavior; add Docker terminal resizing and fuller template settings.
4. Add VMware, VirtualBox, and IOU behind explicit capability-checked adapters, then expand endpoint compatibility and `.gns3` import/export.
5. Decide whether a later client compatibility layer needs `/v2` aliases or should track a Web UI revision aligned with server 3.1.
