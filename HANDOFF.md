# Development handoff

Updated: 2026-10-18

## Project objective

Build a reliable Rust network-lab controller by reverse engineering the GNS3 3.1 server and Web UI. The evidence and scope decisions are in [docs/reverse-engineering.md](docs/reverse-engineering.md); the compact REA report is in [docs/evidence/gns3-web-ui-rea-summary.json](docs/evidence/gns3-web-ui-rea-summary.json).

## Current implementation

- The Axum controller persists projects and topology in SQLite. It exposes a selected GNS3-shaped `/v3` API, atomic topology snapshots, and replayable project events over WebSockets.
- Docker nodes use real local images and containers, lifecycle operations, and `--network none`. Each link endpoint gets a veth moved into the running container namespace (`port_number` 0 maps to `eth0`) and a uBridge Ethernet NIO; the veth host peer joins that endpoint's UDP link tunnel.
- QEMU nodes use local disk images, linked-clone or direct HDA–HDD disks, QMP lifecycle control, and KVM with TCG fallback. Runtime launch supports CD-ROM, BIOS, kernel/initrd, boot order, TPM/UEFI, QEMU options, process priority, and close actions. Every link endpoint uses a QMP socket UDP netdev and an isolated uBridge endpoint; the NET-owned NIC path issues QMP hot-add commands while running. The installed CHR image did not expose NICs added after the OS was fully booted, so live QEMU packet checks attached links before node start. The selected platform must match the configured `qemu-system-*` binary.
- VPCS nodes launch the upstream BSD-licensed `vpcs` executable as a managed process, expose its Telnet console through a WebSocket, and forward raw Ethernet frames over local UDP sockets. Shutdown uses the VPCS console's quit path and waits for its forked PC process to exit, avoiding orphan emulator children. VPCS has one adapter and no suspend operation yet.
- Classic IOS and IOSv are separate paths: the Dynamips adapter manages all seven upstream platform families, uses real IOS ELF images, applies chassis/module/WIC and runtime settings, exposes router lifecycle and console operations, and binds a UDP NIO into the same per-endpoint uBridge tunnel model as QEMU and VPCS. IOSv/IOSvL2 disk appliances still use QEMU. The repository does not contain a Cisco IOS image, so a router boot and router-to-VPCS ping have not been verified.
- Running QEMU VMs expose a serial socket that the Rust controller bridges to a WebSocket. The TanStack Start UI attaches xterm.js in a docked, minimizable console area at the bottom of the screen; multiple consoles remain mounted in tabs while hidden. Each runtime-specific console route validates that node type and running state, and QEMU cleanup removes stale serial sockets.
- Docker nodes are created with stdin and a TTY enabled. The `/v3/compute/projects/{project_id}/docker/nodes/{node_id}/console/ws` route attaches to the running container TTY and streams raw input/output to xterm.js; disconnect sends Docker's detach sequence so an interactive container remains running. This uses `script` from util-linux to provide the PTY Docker CLI requires.
- Runtime status reports whether the service account can access `/dev/kvm` and returns the operating-system error when it cannot. The `teodor` account and current session now have `kvm` group access, and a QEMU launch with explicit `-accel kvm` succeeded.
- The browser UI uses TanStack Start in SPA mode with typed project routes and shadcn/ui components (Radix, Tailwind CSS v4). The Rust server serves the built static shell and assets alongside the API; Node is needed to build and develop, not to run the deployed controller.
- The project UI has a topology-first workspace: central draggable map, left-side device library and topology summary, template drag-and-drop with automatic device names, rename and lifecycle actions from the selection panel/context menu, per-device Configure for stopped QEMU/Docker/VPCS/Dynamips nodes and always-running builtin nodes, duplicate, explicit interface-port connection mode, and start/stop-all actions. Global template settings are persisted and copied when a new node is added. Docker per-device edits replace the stopped container while preserving configured persistent paths; the replacement becomes active only after it is fully created.
- The appliance library and project palette use only imported GNS3 `.gns3a` definitions and explicitly created custom appliances. Installed runtime images are exposed only as inputs in the custom-appliance form; image discovery never silently creates an appliance. Custom QEMU, Dynamips, Docker, and VPCS definitions are saved as `.gns3a` files in the same global library. The manager shows runtime settings and image requirements by appliance version, inspects global image hashes/sizes, suggests matching local files, stores explicit image-to-slot bindings, and records a deliberate checksum/size override. A template appears in the project palette only when its runtime and required supported image slot are available. The image catalog is opened as a modal.
- Configure menus and forms are based on the supplied GNS3 Web UI's `context-menu.component.html`, `config-action.component.ts`, QEMU/Docker/VPCS node configurators, and appliance wizard. This controller intentionally exposes only settings its runtime launch path consumes: QEMU RAM, vCPUs, adapter count/model, primary disk interface, boot priority; Docker image, adapter count, CPU/memory limits, command, environment, extra hosts, persistent paths; VPCS startup script; and Dynamips startup config. Dynamips platform, chassis/slot and NVRAM are global-template settings because an existing hypervisor needs recreation before they can safely change.
- The image catalog searches the GNS3 registry for `.gns3a` appliance definitions and iShare2/LabHub. GNS3 definitions import as actual appliance JSON. Selected QEMU disk and single-file Dynamips IOS entries can download into the global image folders with the LabHub size and MD5/SHA1 checks; IOS images also pass Dynamips ELF validation. It does not run iShare2's EVE-NG installer. IOL and archived QEMU packages remain unsupported.
- Ethernet links are GNS3-style point-to-point UDP tunnels between two node adapters. A uBridge userspace relay per endpoint joins the tunnel to Docker's veth or the QEMU/VPCS/Dynamips UDP adapter. Link creation supports running nodes; stop/start/reload reattaches the saved endpoint ports, and startup reconciles links for runtimes that survived controller restart. Adapter indices and UDP assignments are stored on each endpoint so controller restart does not change the topology wiring. QEMU hot-add uses QMP `netdev_add`/`device_add`; the live CHR guest did not enumerate NICs added after full boot, and live CHR packet verification therefore used links created before start. Startup recovery is implemented but was not verified by restarting the controller process live. `suspend`, frequency drop, packet loss, delay with jitter/distribution, corruption, BPF, link style, endpoint labels, and packet capture start/stop/file/stream routes are persisted or applied. The available filters match relay-supported GNS3 filters; Web Wireshark launch is not available. Docker interfaces receive stable locally administered MAC addresses. The operator granted `cap_net_admin,cap_net_raw=ep` to the user-local uBridge binary; `/v3/runtimes` reports uBridge available.
- Links require exactly two endpoints, as in GNS3's `LinkCreate`/`LinkUpdate` schemas. The previous port's shared-segment behavior is removed; a switch or hub must be an explicit node.
- Base images are shared across all projects. Default QEMU and Dynamips directories are `$XDG_DATA_HOME/network-simulator/images/{qemu,dynamips}` or `~/.local/share/network-simulator/images/{qemu,dynamips}`; `NETWORK_SIMULATOR_IMAGE_HOME` moves both, and each runtime has its own path override. Startup creates the directories. QEMU accepts uploaded disk images validated by `qemu-img` (64 GiB max); IOS upload keeps its ELF validation. Docker images remain in the global Docker Engine store. VPCS and Dynamips binaries can be installed per-user in the app data `bin/` folder and are detected there automatically. Per-node QEMU overlays and hypervisor state remain in runtime state directories.
- Previous `#/projects/<id>` URLs redirect to `/projects/<id>`. The frontend uses the target server's `/v3` API; the supplied upstream UI snapshot calls `/v2`.
- Unsupported node types are rejected. There are no fake runtime implementations for unported hypervisors.

## Runtime parity workstream

- `docs/runtime-parity.md` compares the GNS3 3.1 writable compute-node fields and runtime behaviors with the port, including QEMU/Docker/Dynamips/VPCS template-only settings and known gaps.
- QEMU launch handles HDA–HDD linked-clone/direct disks and interfaces, explicit backing-file overrides, per-node overlay reset requests, cached MD5 metadata, a private raw config disk when `config.img` is configured, CD-ROM/BIOS/kernel/initrd/append, boot priorities, QMP close behavior, console modes, TPM/UEFI, process priority, CPU throttling, and runtime-scoped disk create/resize/delete helpers. Additional QEMU options use a safe allowlist; host-file, host-device, monitor, and controller-owned options are rejected. Imported disk/support paths are revalidated against the configured image and node directories. Supplied MD5 values are reported but not compared. `config.zip` import/export and diskless guests remain incomplete; QEMU custom MAC/carrier behavior remains with NET.
- Docker supports HTTP/HTTPS host TCP bridges to `console_http_port`, VNC through Xvfb+x11vnc when installed, `console_type: none` in runtime and node configuration, and a separate aux PTY WebSocket backed by `docker exec`. Missing VNC tools produce an explicit unsupported error. HTTP path/resolution and VNC resolution are carried with node metadata. Docker container IDs are checked against ownership markers in the Docker runtime state directory before lifecycle, console, resize, or removal operations. Docker Engine TTY resize remains wired to a JSON WebSocket control frame (`type=resize`, `rows`, `columns`); the frontend still needs to emit that frame. `extra_configs` and `startup_config_content` remain unsupported.
- Dynamips applies platform/chassis/module/WIC, memory, clock/mmap, idle, disk, NVRAM, MAC/system ID, console, and startup/private configuration settings. Router names are validated and quoted protocol strings escape control characters. Runtime working/log/ghost paths and hypervisor/console ports must match a controller-written per-node manifest. It generates a missing ghost IOS cache with a temporary Ghost router when mmap is enabled, and the Idle-PC proposal/auto-selection routes use runtime helpers. Auto-delete removes matching hypervisor disk artifacts without deleting config files. There is no licensed IOS image in this checkout, so ghost generation and router boot are unit-tested only.
- VPCS writes/clears startup scripts with `%h` expansion and resolves a relative `base_script_file` from the project's DB-backed files when no inline script is supplied. Per-node state supports multiple instances. Console auto-open, non-Telnet console modes, and suspension remain incomplete.
- NET owns NIC/NIO attachment and link behavior. Named `TODO(RUNTIME-NET ...)` hooks in the runtime mark custom adapter/MAC/carrier integration and VPCS suspension without changing NET's files or link path.
- Runtime tests cover QEMU command construction, option allowlisting, disk helpers and imported-path rejection; Docker create/TTY resize, console modes, and container-ID ownership; Dynamips platform commands, Ghost IOS mmap requirements, protocol quoting and imported-runtime validation; and VPCS startup files/base scripts. The QEMU live start/stop through QMP and Docker live HTTP/AUX console checks passed. The full Rust suite reports 94 passed, 3 failed, and 15 ignored. The remaining failures are API test fixtures: the Dynamips Idle-PC fixture has runtime paths/ports but no controller ownership manifest, and two QEMU tests assume there are no runtime templates even though their test router provides `router.qcow2`. Docker `console_type: none` is accepted by runtime and node configuration. VNC reports a clear unsupported error when Xvfb/x11vnc are missing; neither tool is installed here. No Dynamips executable, VPCS executable, or licensed IOS image is available here.
- `rustfmt --check` passes on the runtime-owned Rust files. `cargo fmt --all -- --check` still reports formatting differences in shared `src/api.rs`; it was left untouched rather than reformatting the API/NET-owned code outside this workstream.

## Built-in node parity workstream

- `src/builtin/mod.rs` implements Ethernet switch, Ethernet hub, Cloud, and NAT nodes on NET's two-endpoint link engine. Builtin templates are included in `/v3/templates`; template creation and direct node creation persist GNS3-shaped top-level `ports_mapping` data in the existing topology JSON store, so this work adds no migration.
- Switches default to eight access ports and the Rust L2 forwarder learns unicast MAC addresses per VLAN, floods unknown/broadcast frames within that VLAN, and handles access, dot1q, and QinQ tag modes. Hub ports flood frames to every other connected port. Cloud endpoints map host Ethernet, TAP, or external UDP NIOs; on Linux, physical interfaces use uBridge raw Ethernet and bridge interfaces use a temporary TAP enslaved to the selected bridge. NAT maps its single host-side NAT interface through that same bridge-aware path.
- Builtins stay `started` and reject start/stop/suspend/reload lifecycle operations. `/v3/projects/{project_id}/nodes/{node_id}/config` accepts flat `name`, `ports_mapping`, switch `console_type`, and Cloud remote-console fields as appropriate for the node type. It accepts legacy `{ "properties": { ... } }` input additively but stores normalized fields at the top level. Switch VLAN edits update its forwarding table while connected; Cloud mapping edits detach and reattach its link endpoints.
- The built-in node editor reads top-level fields and submits flat configuration patches. NAT uses the configured host interface, normally libvirt's `virbr0`; the default libvirt network must be active. uBridge needs `CAP_NET_ADMIN` and `CAP_NET_RAW` (or root privileges) to attach host interfaces and create/manage link interfaces. These privileges apply to the controller's configured uBridge binary.
- Unit coverage exercises VLAN classification, per-VLAN MAC learning/isolation, QinQ/dot1q tagging, hub flooding, Cloud/NAT NIO selection, and invalid configuration. HTTP coverage includes template listing/creation, persistence, always-running lifecycle behavior, and flat-field configuration. The frontend test verifies the editor submits flat fields, and the full UI suite passes (88 tests). Live Docker/VPCS/uBridge tests passed for switch pings among three Docker hosts plus VPCS with access-VLAN isolation, hub forwarding, and bidirectional Cloud UDP NIO frames. A Docker host also reached the external network through the active libvirt `virbr0` NAT path. The live checks assert endpoint and Linux TAP/veth cleanup; the Cloud physical-interface raw NIO and user-supplied TAP mappings have unit/config coverage but were not exercised live. uBridge's configured binary needs `CAP_NET_ADMIN` and `CAP_NET_RAW` (or root privileges); this host's default libvirt network was active during the NAT check.
